# Домен и модель данных Job Hunter

> Дата: 2026-10-13. Источник правды по сущностям, идентичности, жизненному циклу и пулам.
> Связи: `PLAN.md` §3 (архитектура), `docs/requirements.yaml` (FR-008…FR-010, NFR-008), `docs/adr/0006-hot-cold-liveness.md`.

## 1. Сущности и ключи

| Сущность | Ключ | Где живёт | Назначение |
|---|---|---|---|
| `Vacancy` (запись о вакансии) | **(source, external_id)** — уникально | таблица `vacancies` | нормализованное объявление + метаданные наблюдений |
| Наблюдения (метаданные) | те же (внутри строки) | поля `first_seen_at`, `last_seen_at`, `times_seen`, `content_hash` | живость, частота появлений, детект изменений |
| `VacancyState` (воронка владельца) | `record_id` (FK) | `vacancy_states` | **другая ось**: interested/applied/interview/… — про человека, не про вакансию |
| `HiddenEmployer` | `employer_name` | `hidden_employers` | скрытие работодателя из выдач |
| `LLMCache` | `sha256(role|promptver|input)` | `llm_cache` | не дёргать модель дважды |
| Watchlist компаний (план, FR-001) | `(type, external_id)` | будущая `watchlist_companies` | компании-мечты, частый опрос |
| Employer-агрегаты (производные) | `employer` (нормализованное имя/ИНН) | вычисляются; агрегаты сохраняем | «10 публикаций за 3 месяца», доля вечных |
| Профиль/настройки | файл | `config/profile.yaml`, `settings.yaml` | не в БД (C1: персданные отдельно от данных поиска) |

## 2. Две независимые оси состояния (не смешивать!)

1. **Liveness** — жизнь вакансии у источника (вычисляемая): `active → stale → gone → (retention/archived)`.
2. **Funnel** — статус у владельца (ввод владельца): `new → interested → applied → responded → interview → offer | rejected | archived`.

Одна ось не влияет на другую: вакансия может быть `gone` (у площадки) и `interview` (у вас).

## 3. Идентичность: жёсткая и мягкая

**Жёсткая (`source`+`external_id`)** — детерминированный dedupe:
| Тип источника | external_id | Риски |
|---|---|---|
| API с id (hh, SuperJob, Trudvsem, Habr) | id площадки (строкой) | переиспользование id — редкое |
| Порядковый номер площадки | номер как есть | перенумерация/переиспользование |
| RSS | `guid`, иначе хеш каноничного URL | нет guid → правка текста создаёт «новый» id |
| Telegram (план) | `channel:message_id` | удалённые посты = пропажи |
| Крайний фолбэк | `sha1(title|employer|description)` | любая правка = «новый» id |

**Мягкая (кластеры)** — для перепостов, кросс-источников и источников без стабильного id: группировка по работодателю + нечёткому сходству названия (rapidfuzz, порог `repost_similarity`). Каноническая запись — свежайшая; в UI/отчёте видно происхождение.

## 4. Жизненный цикл записи (сценарий «слесарь-аналитик»)

| День | Факт | Что в базе |
|---|---|---|
| Д1 | пришла с hh (id=123) | **1 строка**: first_seen=Д1, last_seen=Д1, times_seen=1 |
| Д2 | тот же id снова | **та же строка**: last_seen=Д2, times_seen=2 (не дубль) |
| Д3 | исчезла из выдачи | строка **остаётся**: last_seen=Д2; не удаляем |
| ДN (порог stale) | нет появлений > X дней | liveness = `stale` (вычисляется на чтение) |
| ДM (порог gone) | нет появлений > Y дней | liveness = `gone`: уходит из горячего пула, участвует только в аналитике |
| перепост | перевыложили с новым id | новая строка + кластер (штраф «перепост/пул»), canonical — свежайшая |

Пороги X/Y — конфигурируемые (`scoring.yaml`), дефолты фиксируются в реализации FR-009.

## 5. Горячий и холодный пулы (без физического сплита БД)

- **Горячий** = `active` (и, при желании, `stale`): дайджест, списки, воронка, отчёты.
- **Холодный** = `gone`: только аналитика работодателя/рынка. Сырьё живёт по **retention-политике** (по умолчанию 12 мес), агрегаты («публикаций за квартал», доля вечных) — **бессрочно** в производных таблицах.
- Реализация: одно физическое хранилище + `liveness` и фильтры/представления. Обоснование — `docs/adr/0006-hot-cold-liveness.md` (транзакции, бэкап, отсутствие кросс-БД джойнов; выигрыш от физсплита на наших объёмах ~0).

## 6. Дубли: правила поведения

| Ситуация | Поведение |
|---|---|
| тот же (source, id) | UPDATE строки, `times_seen += 1` |
| тот же работодатель + похожее название, другой id/источник | отдельные строки + кластер; штраф `repost`; canonical = свежайшая |
| перепост спустя месяцы | новая строка; кластер + история наблюдений показывают паттерн |
| источник без стабильного id | фолбэк-id + кластер (мягкая идентичность) |

## 7. Что сознательно НЕ делаем сейчас (эволюция, если появится боль)

- **Episodes (появления/исчезновения)**: таблица «вакансия появлялась с… по…» — понадобится для точного «10-й раз за 3 месяца»; сейчас хватает `times_seen`, `first/last_seen` и кластеров.
- **Канонизация (`vacancy_groups`)**: схлопывание кросс-источниковых дублей в одну «сущность вакансии» с источниками-ссылками — когда появится реальная потребность (сейчас показываем обе с пометкой честнее).
- **Материализация liveness**: сейчас вычисляем на чтение; материализуем только если hot-путь упрётся в производительность (NFR-008).

## 8. Проверка соответствия коду (на дату)

- `(source, external_id)`-unicity — `UNIQUE (source, external_id)` в БД ✓
- UPDATE при повторной встрече, `times_seen+1` ✓ (`SqlVacancyRepository.upsert`)
- отсутствие удаления при исчезновении ✓
- мягкая идентичность — `find_duplicate_clusters` (rapidfuzz) ✓
- воронка отдельно от liveness ✓ (`vacancy_states`)
- liveness/пулы/retention — **ещё нет** (FR-009, NFR-008)
