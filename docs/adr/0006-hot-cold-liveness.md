# ADR-0006: Горячий/холодный пулы через liveness + представления, а не физический сплит БД

- **Дата:** 2026-10-13
- **Статус:** accepted
- **Связанные документы:** docs/DOMAIN.md §5, requirements.yaml FR-009, NFR-008, PRODUCT.md C1/C8

## Контекст
Владелец предложил разделить данные: горячий пул (актуальные вакансии) и холодный (историческое сырьё для аналитики работодателей: «выложил 10-й раз за 3 месяца»). Объём сейчас ~десятки тысяч строк максимум; всё локально (C1), данные до v1.0.0 можно чистить (C8).

## Варианты
1. **Физический сплит**: отдельная БД/файл (или отдельная таблица-архив) под историю.
2. **Статус + представления**: одна БД; liveness (`active/stale/gone`) вычисляется/материализуется; горячие запросы фильтруют, аналитика читает всё; retention сырья + бессрочные агрегаты.
3. Оставить как есть (без разделения): простое, но горячий путь со временем начнёт расти на мёртвых записях.

## Решение
Вариант 2. Критерии: одна транзакционная граница (ingest обновляет и «горячее», и «холодное»), бэкап = один файл (C1/ADR-0001), нет кросс-БД джойнов для аналитики работодателя, а выигрыш варианта 1 на текущих объёмах близок к нулю. Retention применяем к **сырью** `gone`, агрегаты храним бессрочно.

## Последствия
- Плюс: простота, дешёвый бэкап, аналитика «по всем» бесплатна; пороги liveness конфигурируемы.
- Минус: горячие запросы обязаны дисциплинированно фильтровать liveness (закреплено NFR-008 + индекс).

## Миграционный путь к физическому разделению (требование владельца 13.10 → NFR-009)
Разделение допускается в будущем, поэтому решение обязано быть migration-ready:
1. `liveness` — первоклассное поле с индексом; решения по фильтрам не полагаются на «физическое соседство».
2. Единственная точка доступа к данным — репозитории-порты; прямой SQL вне `infrastructure/db` запрещён.
3. Вынос холодного сырья оформляется как миграция `vacancies → vacancies_archive` (таблица или отдельный файл) по `gone` + retention, с read-совместимостью через репозиторий/представление.
4. Производные агрегаты (Employer) не держат FK на сырьё — значит вынос не ломает аналитику.
5. План выноса и критерий триггера (например, hot > 50k или p95 > порога NFR-001) фиксируются; триггер пока не достигнут.
