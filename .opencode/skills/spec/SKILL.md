# Спецификации и требования Job Hunter

## Когда использовать
Перед реализацией любой фичи; при изменении поведения/интерфейсов; при принятии архитектурного решения; при добавлении источника; когда пользователь спрашивает «где это задокументировано».

## Порядок (Definition of Ready → Done)

**DoR (до кода):**
1. Сценарий/флоу — в `docs/DISCOVERY.md` §5 (F*) или `docs/UI_SCENARIOS.md`.
2. Если трогает приватность/источники/ресурсы/стек — запись в реестре ограничений `docs/PRODUCT.md` §3 (C*).
3. Требование в `docs/requirements.yaml`: `id`, `statement` (проверяемо), `acceptance[]`, `priority`, `release`, `traces` (F*/C*), `status: accepted`.
4. Архитектурно спорное решение → ADR по `docs/adr/0000-template.md`.

**DoD (код готов):**
1. Тесты названы по ID требования (`tests/test_*.py::test_fr_042_*`), в реестре `tests: [...]`, `status: done`.
2. Гейты зелёные: `uv run ruff check src tests && uv run mypy src && uv run pytest`.
3. Запись в `CHANGELOG.md` со ссылкой на ID.
4. Валидатор: `uv run pytest tests/test_requirements_registry.py`.

## Ленивость (важно)
- Запись в реестр появляется **в момент actionable-шага**, не заранее. Никаких ретро-требований «на всякий случай».
- Ретро покрываем только при касании соответствующей фичи.
- Пустой/частичный реестр — это нормально; строгость правил растёт с записями (валидатор уже проверяет уникальность ID и трассы).

## Форматы
- Требования — `docs/requirements.yaml` (схема v1, поля в шапке файла). **Не БД:** требования обязаны ревьюиться в git-диффе.
- ADR — `docs/adr/NNNN-название.md`, нумерация сквозная.
- Проза-объяснения — `docs/PRODUCT.md`, `docs/DISCOVERY.md`; реестр — только факты со ссылками, без дублирования прозы.

## Кто чем пишет (экономика моделей)
| Работа | Исполнитель | Модель |
|---|---|---|
| Черновики требований/ADR/TESTING, механическая правка документов | субагент `specwriter` | deepseek-v4.1-flash:cloud |
| Разведки фактов для требований | субагент `scout` | gpt-oss:120b-cloud |
| Ревью и финальные решения | основной агент | по сессии |
| Спорные архитектурные последствия | субагент `deepreview` | kimi-k3#high (точечно) |

## Запрещено
- Писать требования «из головы» без трассы на сценарий/ограничение или на исследование/источник.
- Дублировать содержание PRODUCT/DISCOVERY в реестре.
- Ставить `status: done` без тестов и записи в CHANGELOG (валидатор упадёт).
