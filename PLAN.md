# Job Hunter — проект сервиса-ассистента поиска работы

> Статус: **черновик на согласовании** (v0.1, 2026-10-12)
> Реализация начинается только после утверждения плана и закрытия открытых вопросов (раздел 9).

---

## 1. Видение

Локальный, приватный сервис, который:

1. Собирает вакансии из **подключаемых источников** (плагины, без пересборки проекта).
2. Нормализует, дедуплицирует и **ведёт историю наблюдений** за вакансиями.
3. Анализирует каждую вакансию: свежесть/«вечность», перепосты, одиночная роль или пул смежных профессий, качество условий, сигналы о работодателе.
4. Ведёт **профиль кандидата** (навыки, опыт, предпочтения, запреты).
5. Сопоставляет профиль с вакансиями и выдаёт **ранжированный список с объяснимыми оценками** — от наиболее интересных к наименее.
6. Использует **локальные LLM** (Ollama / LM Studio, OpenAI-совместимый API) там, где правила не справляются; при недоступности LLM деградирует до чистых эвристик.

## 2. Принципы

- **Clean Architecture**: `domain` не знает о БД, HTTP и LLM; инфраструктура подключается к портам.
- **Plugin-first**: источники вакансий, скореры и экспорты — плагины (entry points + YAML-конфиг). Добавление источника = новый пакет + строка в конфиге, без правок ядра.
- **Explainable scoring**: итоговая оценка = взвешенная сумма сигналов, каждый сигнал имеет машинную причину + человекочитаемое объяснение. Никаких «магических» чисел.
- **Graceful degradation**: LLM опциональна; система полностью работоспособна на правилах.
- **Локальность и приватность**: данные в локальной БД, LLM локальная, сеть — только к источникам вакансий.
- **Каноничная инженерия**: типизация (mypy strict), линт (ruff), тесты (pytest), миграции (Alembic), conventional commits, CI-чеки.

### 3.2 Пайплайн данных

```
connectors → normalize → dedup(хэш + нечёткое сходство) → observations(история)
           → analyze(rules → LLM-структуризация) → score(hard filters → skills match → LLM verdict)
           → rank → report(md/csv/json / web)
```

Каждый шаг — отдельный use-case, вызываемый из CLI/планировщика; промежуточные результаты персистентны (можно пересчитать скоринг без повторного сбора).

## 4. Предметная модель (ключевые сущности)

| Сущность | Назначение |
|---|---|
| `Vacancy` | Нормализованная вакансия: источник+id, url, title, company, локации, remote-режим, вилка/валюта, published_at, описание (raw+text), навыки, занятость, грейд |
| `Observation` | История: first_seen / last_seen, счётчик появлений, снапшоты изменений — база для «давно висит» и детекта перепостов |
| `Employer` | Компания: имя, сайт, агрегированные сигналы (частота перепостов, срок жизни вакансий), опц. внешние рейтинги |
| `CandidateProfile` (версионируемый) | Навыки+уровни, грейд, зарплатные ожидания, предпочтения (стек, домены, формат), deal-breakers, «нравится/не нравится» |
| `Analysis` | Структурный разбор вакансии: свежесть, тип (одна/пул), качество описания, красные флаги, оценка условий, заметки о работодателе — каждый пункт с `source: rule\|llm` и `evidence` |
| `Score` | Итог: components → weighted total, verdict, текстовое объяснение, ссылка на версию профиля |

## 5. Аналитика (что и как считаем)

1. **Свежесть/«вечность»**: `published_at` vs `first_seen`; перепост = высокое сходство текста + тот же работодатель при новом `published_at`; «вечная вакансия» — наблюдается > N дней/перепостов ≥ K.
2. **Одиночная роль vs пул смежных профессий**: кластеризация по навыкам/эмбеддингам + градация «это одна позиция / зонтик из ролей / массовый найм».
3. **Оценка условий**: вилка против ожиданий и рынка (локальная статистика из собранных данных), валюта «по запросу» — штраф, remote/гибрид, бонусы из текста (LLM-извлечение), переработки/онколл — красный флаг.
4. **Оценка работодателя**: паттерны публикаций (вечные вакансии, зонтики), LLM-чтение текста (токсичные паттерны, «молодая динамичная команда»), опц. внешние рейтинги плагином.
5. **Сопоставление с профилем**: hard-фильтры (локация, занятость, мин. зарплата, deal-breakers) → skills overlap (набор навыков; опц. эмбеддинги bge) → rerank (bge-reranker, есть локально) → LLM-вердикт с объяснением.
6. **Красные флаги**: конфигурируемый словарь + LLM-проверка; каждый флаг влияет на оценку.

## 7. LLM-интеграция

- Роли: `extractor` (вакансия → строгий JSON по Pydantic-схеме), `scorer` (профиль×вакансия → verdict+объяснение), `explainer` (человекочитаемые тексты отчёта).
- Structured output (JSON schema), таймауты, ретраи, **кэш по хэшу входа** (LLM не вызывается повторно для неизменившейся вакансии).
- Режим `--no-llm`: только правила.

### 7.1 Ресурсный менеджмент локальных моделей (требование пользователя, 2026-10-12)

Цель: **не выесть ресурсы MacBook** — в любой момент загружена максимум одна модель, после работы она выгружается.

1. **Батч-резидентность**: модель загружается один раз на пакет задач (например, 20 вакансий), между задачами не перезагружается (keep_alive маленький, ~60с). НЕ per-request unload — перезагрузка модели дороже кратного инференса.
2. **Явная выгрузка после батча:**
   - Ollama: финальный запрос с `keep_alive=0` через нативный `/api/*` (OpenAI-совместимый `/v1` keep_alive игнорирует — поэтому для выгрузки используем нативное API).
   - LM Studio: уже настроен auto-unload по бездействию 1 мин (пользовательская настройка) + опционально `lms unload` CLI после батча.
3. **Лимиты**: `max_loaded_models: 1`, `concurrency: 1` (строго последовательно), primary (Ollama) и fallback (LM Studio) **никогда одновременно** — fallback только при недоступности primary.
4. **Выбор модели под ресурсы**: перед загрузкой тяжёлой модели проверяем свободную RAM (psutil); не хватает — деградация к меньшей модели из списка тиров (например, score: 12B → 4B → rules-режим).
5. **Телеметрия**: перед/после батча логируем `/api/ps` (Ollama) — какие модели в памяти и сколько занимают; сторожим от «зависших» моделей.
6. Настройки — `llm.resource_policy` в `config/settings.yaml`.
